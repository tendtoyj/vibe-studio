# Build Check

만든 플로우를 **사용자처럼 처음부터 끝까지 써보고**, 결과를 `docs/REVIEW.md`에 남긴다.

build-slice는 조각마다 그 조각의 확인 기준만 본다. 이 스킬은 조각들이 이어져서 **플로우가 목표 순간까지 끊김 없이 가는지**, 그리고 기획·디자인·문구와 맞는지를 한 번에 본다. 코드 품질 검토가 아니라 **써보는 사람 입장의 점검**이다.

```
┌→ userflow-generator (플로우 그리기 · 바뀐 것 반영)
│      ↓
│  build-spec   (그 플로우를 조각으로 쪼개기)
│      ↓
│  build-slice  (조각 하나씩 만들기 · 반복)
│      ↓
│  build-check  (플로우를 처음부터 끝까지 써보기)   ← 여기
└──────┘
```

## 입력 / 산출물

- **입력:**
  - `docs/SPEC.md` — **필수.** 점검할 플로우 섹션(목표, 조각, 확인 기준)과 작업 기록(달라진 점). 없으면 "먼저 build-spec과 build-slice로 만들어 주세요"라고 안내하고 멈춘다.
  - `docs/FLOWS.md` — 그 플로우의 목표 순간, 단계, 화면 상태, 예외, 첫 버전 범위.
  - `docs/DESIGN.md` — 색·글꼴·모서리, 사용 경계, Do's and Don'ts.
  - `docs/VOICE.md` — 금지선, 쓰는 말, 상황별 톤.
  - `docs/PRODUCT.md` — 플랫폼(기준 화면 크기).
  - 프로젝트 코드 — 앱을 띄우고, 비밀 키를 찾을 때만 읽는다.
- **산출물:**
  - `docs/REVIEW.md` — 점검 결과. 점검할 때마다 맨 위에 새 섹션을 추가한다.
  - `docs/review/` — 스크린샷.
- **하지 않는 것:** 코드 수정, SPEC 체크 변경, FLOWS·DESIGN·VOICE 수정, 플로우 상태 변경. 고칠 것은 build-slice로, 기획에 반영할 것은 userflow-generator로 넘긴다.

---

## 원칙

- **만든 대화와 다른 눈으로 본다.** 같은 대화에서 방금 만든 걸 점검하면 자기가 만든 걸 너그럽게 본다. build-slice와 같은 대화라면 "새 대화에서 build-check를 부르면 더 정확해요"라고 한 번 권한다. 쓸 수 있으면 서브에이전트에게 점검을 맡긴다.
- **진짜 문제만 적는다.** 문제를 찾으라고 하면 없어도 만들어내기 쉽다. 아래 세 종류에 들어가는 것만 문제로 적고, 잘 된 플로우에는 "막힘 없음"이라고 그대로 쓴다. 취향 차이는 문제가 아니다.
- **화면으로 말한다.** 모든 문제에는 스크린샷과 "어디서 무엇을 했더니 무엇이 보였다"를 붙인다. 코드 위치는 쓰지 않는다(고칠 때 build-slice가 찾는다).
- **SPEC 밖은 문제가 아니다.** SPEC의 "흉내만 낼 것"·"이번엔 안 함"에 있는 건 문제로 적지 않는다(로그인이 아무 번호나 통과하는 건 의도된 것이다).

**대화 스타일:** 한국어 기본, 친근한 톤. 사용자는 코드를 읽지 않는다고 가정한다. 결과는 칭찬이나 겁주기 없이 사실대로.

---

## Step 0 — 무엇을 점검할지

- 사용자가 플로우를 말했으면 그것. 아니면 SPEC.md에서 **조각이 다 체크된 가장 최근 섹션**.
- 그 섹션에 체크 안 된 조각이 남아 있으면 알려준다: "조각 3이 아직이에요. 지금까지 만든 데까지만 볼까요?" 사용자가 원하면 만든 데까지만 본다.
- 섹션의 `목표:`(UI 구현 / 기능 구현)를 확인한다. 점검 기준이 달라진다(Step 2).

---

## Step 1 — 처음부터 끝까지 걸어보기

1. **앱을 띄운다.** `.claude/launch.json`이 있으면 Claude 앱의 브라우저 창으로, 없으면 쓸 수 있는 브라우저 도구로 연다. 브라우저 도구가 하나도 없으면 사용자에게 주소와 아래 걸을 길을 체크리스트로 주고, 화면을 캡처해 보내 달라고 한다.
2. **처음 쓰는 사람의 상태로 시작한다.** 브라우저에 저장된 데이터를 지우고(가짜 데이터는 다시 채워지게) 첫 화면부터 연다.
3. **화면 크기는 PRODUCT.md 플랫폼대로.** 모바일 우선이면 폰 너비(390px)로 걷는다. 마지막에 넓은 화면으로 한 번 열어 깨지지 않는지만 본다.
4. **잘 풀리는 길을 걷는다.** FLOWS의 단계 순서대로, 진입부터 **목표 순간**까지. 단계마다 스크린샷을 `docs/review/<YYYY-MM-DD>-F1-01.png`처럼 번호를 붙여 저장한다.
5. **SPEC의 확인 기준을 다시 눌러본다.** 그 섹션의 모든 조각의 기준을 한 번씩. 앞 조각이 뒤 조각 때문에 깨지는 일이 흔하다.
6. **상태와 예외를 건드려본다.** FLOWS의 빈·오류 상태와 예외 중 첫 버전 범위에 들어 있고 눌러서 만들 수 있는 것(빈칸으로 제출, 같은 걸 두 번, 중간에 뒤로 가기, 새로고침).
7. **콘솔 에러**를 단계마다 본다.

---

## Step 2 — 무엇이 문제인가

걸어본 결과를 아래 세 종류로만 나눈다.

| 종류 | 뜻 | 예 |
|---|---|---|
| **막힘** | 목표 순간까지 갈 수 없거나, 확인 기준이 통과하지 않는다 | 요청 보내기를 눌러도 다음 화면으로 안 간다 · 새로고침하면 쓴 메모가 사라진다 · 콘솔에 빨간 에러 |
| **어긋남** | 가긴 가는데 FLOWS·DESIGN·VOICE와 다르다 | FLOWS에 있는 빈 상태 문구가 없다 · 강조색 버튼이 한 화면에 두 개 · VOICE 금지선의 말("즉시", "연체")이 보인다 · 기본 글꼴이 그대로 |
| **위험** | 비밀이 드러나거나 남의 데이터가 보인다 | 아래 "안전 점검" |

**목표가 `기능 구현`이면** 하나 더 본다: 흉내가 남아 있는지. 새로고침하거나 브라우저 데이터를 지운 뒤에도 입력한 게 남아 있는지, 다른 계정으로 들어가면 내 데이터가 안 보이는지. 남아 있는 흉내는 **막힘**이다.

**다듬으면 좋을 것**(문제는 아니지만 눈에 띈 것)은 최대 3개까지만 따로 적는다. 없으면 적지 않는다.

### 안전 점검

사용자에게 결과만 쉬운 말로 알린다. 고치지는 않는다.

- **비밀 키가 코드에 적혀 있지 않은가.** 화면 코드에서 키처럼 생긴 값(`sk-`, `key`, `secret`, `token` 근처의 긴 문자열)을 찾는다. `.env`·`.env.local`이 `.gitignore`에 들어 있고 커밋된 적이 없는지 본다.
- **브라우저로 가는 값에 비밀이 없는가.** Vite의 `VITE_`, Next.js의 `NEXT_PUBLIC_`으로 시작하는 값은 누구나 볼 수 있다. 여기에 비밀 키가 있으면 위험이다.
- **진짜 저장소(Supabase)를 쓰면:** 모든 테이블에 보안 규칙(RLS)이 켜져 있는지, `service_role` 키가 브라우저 코드에 없는지 본다. 확인할 방법이 없으면 "Supabase 대시보드에서 테이블마다 RLS가 켜져 있는지 봐주세요"라고 적는다. 직접 만든 테이블이 아니라 에이전트가 만든 테이블은 RLS가 꺼져 있는 경우가 많다.

## Step 3 — REVIEW.md 저장 (필수 산출물)

**이 스킬의 최종 산출물은 항상 `docs/REVIEW.md` 파일이다.** 채팅에만 보여주고 끝내지 않는다. 날짜는 시스템이 준 오늘 날짜를 쓴다.

- 파일이 없으면 제목과 함께 새로 만든다.
- 있으면 **제목 바로 아래에 새 섹션을 추가**한다(최신이 위). 이전 섹션은 고치지 않는다.

~~~markdown
# Review — {서비스 이름}

> Vibe Studio · build-check · 최신 점검이 위에 있어요

## 2026-10-12 · F1 첫 대여 요청 (목표: UI 구현)

**한 줄 결론:** 목표 순간까지 막힘 없이 가요. 어긋난 곳 2개, 위험 없음.

### 걸어본 길
| 단계 | 화면 | 결과 | 스크린샷 |
|:--:|------|------|------|
| ① | 소개 | 통과 | ![](review/2026-10-12-F1-01.png) |
| ③ | 홈 | 어긋남 1 | ![](review/2026-10-12-F1-03.png) |
| ⑥ | 요청 완료 | 통과 — 목표 순간 도착 | ![](review/2026-10-12-F1-06.png) |

확인 기준 8개 중 8개 통과 · 콘솔 에러 없음 · 넓은 화면 괜찮음

### 문제
| # | 종류 | 어디서 | 무엇이 | 고치려면 (build-slice에 그대로) |
|:--:|------|--------|--------|------|
| 1 | 어긋남 | ③ 홈, 책이 0권일 때 | 빈 상태 문구 대신 빈 화면만 보임 | "홈에서 책이 0권일 때 FLOWS F1 ③의 빈 상태 문구를 보여줘" |
| 2 | 어긋남 | ④ 책 상세 | [요청 보내기]와 하트가 둘 다 강조색 | "책 상세에서 강조색은 [요청 보내기]에만 쓰고 하트는 DESIGN.md의 기본 색으로 바꿔줘" |

### 다듬으면 좋을 것
- 책 카드 제목이 두 줄을 넘으면 잘리지 않고 카드가 길어져요

### 기획과 달라진 점 (→ userflow-generator)
- 책 카드에 '걸어서 몇 분'을 제목 위로 올림 (SPEC 작업 기록 10/11)
- 동네 고르기를 목록 대신 검색창으로 만듦 (화면에서 확인)

### 다음
1. 문제 1~2를 build-slice로 고치기
2. userflow-generator로 "F1 만들었어, 달라진 점 반영해줘" — F1 상태가 UI 구현으로 바뀌어요
3. 다음 플로우는 build-spec으로
~~~

- **기획과 달라진 점**은 SPEC 작업 기록의 "달라진 점"과, 걸어보며 FLOWS와 다르게 만들어진 걸 발견한 것을 모은다. 이건 문제가 아니라 기획에 반영할 거리다.
- **고치려면**은 사용자가 복사해서 build-slice에 바로 넣을 수 있는 한 문장으로, 화면과 기대하는 결과를 쓴다.
- 문제가 없으면 문제 표 대신 `막힘·어긋남·위험 없음`을 쓴다.

## Step 4 — 보고와 다음 안내

한 줄 결론과 문제 수를 말하고, 상황에 맞게 하나를 안내한다.

- **막힘이나 위험이 있으면:**
  > 먼저 고쳐야 할 게 {n}개 있어요. REVIEW.md의 "고치려면" 문장을 build-slice에 하나씩 넣어 주세요. 고친 뒤 다시 build-check를 부르면 다시 걸어볼게요.
- **어긋남만 있으면:**
  > 목표 순간까지는 잘 가요. 어긋난 {n}개는 지금 고칠지 다음에 할지 정해 주세요. 그다음 userflow-generator로 달라진 점을 반영하면 F{n}이 {목표 상태}로 바뀌어요.
- **문제가 없으면:**
  > F{n}이 처음부터 끝까지 잘 가요. userflow-generator로 달라진 점을 반영하고, 다음 플로우로 넘어가요(그리기 → build-spec).

REVIEW.md와 스크린샷은 커밋한다(`점검: F1 첫 대여 요청`). 코드 변경은 없으므로 문서만 담긴다.
