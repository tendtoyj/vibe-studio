Vibe Studio 만들기 고리(build-spec → build-slice → build-check)의 가운데 단계로, 묶음 하나를 만들 때 한 번 부른다(중간에 멈췄으면 다시 불러 이어서 한다).

# Build Slice

`docs/work/`의 작업 묶음에서 **남은 조각을 위에서부터 차례로 모두** 만든다. 조각마다 만들고, 화면에서 확인하고, 저장(커밋)한 뒤 다음 조각으로 넘어간다. 다 만들면 개발 서버를 띄워 둔 채 사용자에게 직접 눌러보라고 알려준다.

```
┌→ userflow-generator (플로우 그리기 · 바뀐 것 반영)
│      ↓
│  build-spec   (그 플로우를 조각으로 쪼개기)
│      ↓
│  build-slice  (조각을 차례로 모두 만들기)   ← 여기
│      ↓
│  build-check  (플로우를 처음부터 끝까지 써보기)
└──────┘
```

## 입력 / 산출물

docs 폴더 구조는 `<스킬경로>/../../assets/LAYOUT.md`를 따른다.

- **입력:**
  - `docs/work/SETUP.md` — **필수.** 정해둔 것(스택·데이터·흉내만 낼 것·이번엔 안 함). 없으면 "먼저 build-spec으로 만들 조각을 정해 주세요"라고 안내하고 멈춘다.
  - `docs/work/{묶음}/SPEC.md` — 이번 묶음의 목표와 조각 목록.
  - `docs/work/LOG.md` — 지금까지의 작업 기록. 있으면 최근 몇 줄을 읽어 이어서 한다.
  - `docs/FLOWS.md` — 조각에 걸린 단계(`F1 ③④`)만 찾아 읽는다. 화면의 핵심 요소·문구·상태·예외가 여기 있다.
  - `docs/DESIGN.md` — 색·글꼴·간격·모서리·컴포넌트 모양, 사용 경계, Do's and Don'ts.
  - `docs/VOICE.md` — 화면 문구. FLOWS에 없는 문구(버튼, 안내, 오류)는 여기 톤으로 쓴다.
  - `docs/DECISIONS.md` — 이미 정한 것.
  - 프로젝트 코드.
- **산출물:**
  - 코드와 커밋 (조각 하나에 커밋 하나가 기본)
  - 다 만든 뒤 켜 둔 개발 서버
  - 묶음 `SPEC.md`의 체크 표시
  - `docs/work/LOG.md`의 작업 기록 (없으면 만든다)
  - 첫 조각에서: 프로젝트, `.claude/launch.json`, `.gitignore`
- **하지 않는 것:** FLOWS.md·DESIGN.md·VOICE.md 수정, 플로우 상태 변경. 만들면서 바뀐 건 LOG.md에 적어두고, 반영은 build-check 뒤에 userflow-generator가 한다.

## 원칙

- **한 묶음만, 조각마다 확인하고 저장.** 이번 묶음의 남은 조각을 순서대로 모두 만들되, 다음 조각은 앞 조각이 확인을 통과하고 커밋된 뒤에 시작한다(몰아서 만들고 마지막에 한 번에 확인하지 않는다 — 깨졌을 때 어느 조각 탓인지 찾기 어렵고 되돌릴 지점이 없다). 다른 묶음, SETUP의 "이번엔 안 함"에 있는 건 만들지 않는다. 하다 보니 필요해 보여도 LOG.md에 "다음에 할 것"으로 적고 넘어간다.
- **멈추는 때.** 아래에서는 남은 조각이 있어도 멈추고 사용자에게 말한다.
  - 같은 문제를 두 번 고쳐도 안 될 때 (Step 5-3)
  - "묻고 나서 하는 것"에 걸릴 때
  - 사용자가 멈추라고 할 때
  - 대화가 아주 길어져 앞에서 정한 것(SETUP·DESIGN 값, 앞 조각의 달라진 점)이 헷갈리기 시작할 때: 지금까지 저장된 데까지 보고하고, 새 대화에서 build-slice를 다시 부르면 남은 조각부터 이어서 한다고 안내한다. 이어서 하는 데 필요한 건 모두 SPEC 체크·LOG.md·커밋에 있다.
- **묻고 나서 하는 것.** 아래는 하기 전에 이유를 쉬운 말로 설명하고 사용자에게 묻는다.
  - SETUP에서 흉내만 내기로 한 걸 진짜로 붙이는 것(로그인, 저장소, 결제, 외부 서비스)
  - SETUP의 스택에 없는 새 라이브러리 설치
  - 이미 만든 화면이나 파일을 지우거나 크게 갈아엎는 것
  - FLOWS와 다르게 화면을 합치거나 순서를 바꾸는 것
- **질문에는 답만 한다.** 사용자가 "이거 왜 이래요?", "이건 뭐예요?"처럼 물으면 설명만 하고 코드를 고치지 않는다. 고칠지는 사용자가 정한다.
- **다 됐다는 말 대신 보여준다.** 조각이 끝났다고 할 때는 확인 기준마다 브라우저에서 눌러본 결과(스크린샷)를 근거로 댄다. 직접 확인하지 못한 기준은 "확인 못 함"이라고 그대로 말한다.
- **비밀 키는 코드에 쓰지 않는다.** API 키 같은 값은 `.env.local`에만 두고, 사용자가 직접 붙여 넣게 안내한다. 프로토타입(Vite)에서는 키가 필요한 기능을 만들지 않는다(SETUP대로 흉내 낸다).

**대화 스타일:** 한국어 기본, 친근한 톤. 사용자는 코드를 읽지 않는다고 가정한다. 파일 이름이나 코드 대신 **화면에서 무엇이 달라지는지**로 말한다. 기술 용어는 처음 한 번 쉬운 말로 풀어 쓴다.

## Step 0 — 무엇을 할지 정하기

사용자의 말로 모드를 정한다.

- **만들기** — "만들어줘", "다음 조각", "이어서" → Step 1.
- **고치기** — "이상해요", "안 돼요", "고쳐줘"처럼 문제를 말하면 → Step 5.
- **되돌리기** — "되돌려줘", "아까로 돌아가줘" → Step 6.

**만들 조각 고르기:** 사용자가 묶음을 말했으면 그것. 아니면 `docs/work/`에서 **순번이 가장 낮고 체크 안 된 조각이 남은 묶음**을 고르고, 그 SPEC.md에서 **위에서부터 체크 안 된 조각을 차례로 모두** 만든다. 사용자가 특정 조각만 말했으면("조각 2만 만들어줘") 그 조각 하나만 한다. 시작할 때 "{묶음 이름}의 조각 {n}~{m}을 차례로 만들게요. 조각마다 눌러보고 저장하면서 갈게요"라고 어느 묶음에서 몇 개를 만드는지 밝힌다. 모든 묶음이 다 체크돼 있으면 "만들 조각을 다 만들었어요. build-check로 처음부터 끝까지 써볼까요? 다음 일은 build-spec으로 새 묶음을 만들어요"라고 안내하고 멈춘다.

**스택이 바뀌었는지:** SETUP의 스택이 실제 코드(`package.json`)와 다르면(예: SETUP은 Next.js인데 코드는 Vite), 다음 조각 전에 **옮기기**를 먼저 한다 → Step 1-2. 보통은 build-spec이 만든 옮기기 묶음의 조각 1이 이 일이다.

## Step 1 — 시작 전 준비

### 1-1. 첫 조각이면: 프로젝트 만들기

코드가 없으면 조각을 만들기 전에 프로젝트를 준비한다. 사용자에게는 "앱을 담을 그릇부터 만들게요" 정도로만 말한다.

1. **Node.js 확인.** `node -v`로 확인한다. 없으면 설치 방법(공식 사이트 LTS 버전)을 안내하고 멈춘다. 직접 설치하지 않는다.
2. **프로젝트 생성.** SETUP의 스택대로, 공식 생성 명령을 질문 없이 끝나는 옵션으로 현재 폴더에 만든다. 언어는 SETUP 스택대로 TypeScript다(에러를 미리 잡아줘서 고치기 쉽다). `docs/`는 그대로 둔다.
   - 프로토타입: Vite의 React + TypeScript 템플릿 + Tailwind CSS
   - 실제 기능: Next.js(App Router, TypeScript, Tailwind CSS)
3. **디자인 준비.** DESIGN.md의 색·글꼴·모서리·간격 값을 Tailwind 설정의 테마로 옮기고, `runtime_deps`의 아이콘·글꼴을 설치한다. 값은 DESIGN.md에 적힌 그대로 쓰고 짐작해서 바꾸지 않는다.
4. **가짜 데이터.** SETUP "데이터"에 적힌 양만큼 가짜 데이터를 한 파일에 모은다. 내용은 서비스에 맞게 그럴듯하게(동네책장이면 실제 있을 법한 책 제목). 브라우저에 저장해 새로고침해도 남게 한다.
5. **`.gitignore`** 에 `.env`, `.env.local`, `node_modules`가 들어 있는지 확인한다.
6. **`.claude/launch.json`** 을 만든다. Claude 앱의 브라우저 창이 이 파일을 보고 앱을 띄운다.
   ```json
   {
     "version": "0.0.1",
     "configurations": [
       { "name": "app", "runtimeExecutable": "npm", "runtimeArgs": ["run", "dev"], "port": 5173 }
     ]
   }
   ```
   포트는 Vite면 5173, Next.js면 3000.
7. **git.** 저장소가 아니면 `git init`. 이 시점을 첫 커밋으로 남긴다("프로젝트 준비").

### 1-2. 스택을 옮길 때 (프로토타입 → 실제 기능)

SETUP이 Next.js로 바뀌었는데 코드가 Vite면, 이걸 하나의 조각처럼 다룬다.

- 새 Next.js 프로젝트로 화면·디자인 설정·가짜 데이터를 옮긴다. 화면은 모습이 바뀌지 않게 옮긴다.
- SETUP의 **"옮길 때 다시 볼 것"** 을 하나씩 본다. 이번에 진짜로 붙이지 않는 것은 흉내 그대로 두되, 키·로그인·데이터 저장이 들어갈 자리는 서버 쪽에 만든다.
- 브라우저로 전달되는 코드에 비밀 값이 없는지 확인한다(`NEXT_PUBLIC_`으로 시작하는 값은 브라우저에 그대로 보인다).
- 확인 기준: 모든 묶음에서 이미 체크된 조각들의 확인 기준을 다시 눌러봐서 모두 통과한다.
- LOG.md에 "Vite → Next.js로 옮김"을 남긴다.

### 1-3. 할 일 말하기

**조각마다** 만들기 전에 **3줄 이내로** 말한다: 이번 조각에서 화면에 무엇이 생기는지, 흉내 내는 게 있으면 무엇인지, 다 되면 어떻게 확인하는지. 사용자가 멈추라고 하지 않으면 바로 시작한다(허락을 기다리지 않는다).

> 이번엔 홈 화면을 만들게요. 지도 모양 그림 위에 책장 점이 찍히고, 아래로 책 카드 20장이 보여요. 다 되면 카드를 눌러 책 상세로 가는지, 책이 없을 때 안내 문구가 뜨는지 확인할게요.

## Step 2 — 만들기

Step 2~4는 **조각 하나 단위**다. 한 조각이 Step 4(저장)까지 끝나면 남은 조각이 있는 한 1-3으로 돌아가 다음 조각을 시작한다.

- **화면 구성은 FLOWS에서.** 해당 단계의 핵심 요소를 위에서 아래 순서대로, 주 행동(다음 단계로 가는 조건)과 화면 이동까지 만든다. 이 조각에 걸린 빈·오류 상태와 예외도 만든다.
- **모습은 DESIGN에서.** 1-1에서 옮긴 테마 값만 쓴다. 사용 경계(예: 강조색은 화면당 주요 행동 하나에만)와 Don'ts를 지킨다. 디자인 지시가 없는 부분은 DESIGN.md의 가장 비슷한 컴포넌트를 따르고, 기본 템플릿 모양을 그대로 두지 않는다.
- **문구는 FLOWS → VOICE 순서로.** FLOWS에 적힌 문구는 그대로 쓴다(`(임시)` 표시는 화면에 넣지 않는다). FLOWS에 없는 문구는 VOICE.md의 실제 문구·쓰는 말·금지선을 따라 쓴다.
- **화면 크기는 PRODUCT.md 플랫폼대로.** 모바일 우선이면 폰 너비(390px)를 먼저 맞춘다.
- **흉내는 SETUP에 적힌 방식대로.** 흉내 낸 부분은 코드에 `// 흉내: 로그인 — 아무 번호나 통과 (SETUP)`처럼 한 줄 표시를 남겨, 나중에 진짜로 바꿀 곳을 찾기 쉽게 한다.

## Step 3 — 화면에서 확인하기

1. **앱을 띄운다.** 첫 조각에서 띄우고, 이후 조각에서는 켜져 있는 걸 그대로 쓴다(꺼졌으면 다시 띄운다). Claude 앱의 브라우저 창이 있으면 `.claude/launch.json`으로 띄운다. 없으면 쓸 수 있는 브라우저 도구(Chrome, Playwright 등)로 연다. 브라우저 도구가 하나도 없으면 사용자에게 주소를 알려주고, 확인 기준을 체크리스트로 주며 눌러봐 달라고 한다.
2. **확인 기준을 하나씩 눌러본다.** SPEC에 적힌 순서대로, 사람이 하듯 클릭하고 입력한다. 기준마다 스크린샷을 남겨 사용자에게 보여준다(파일로 저장하지 않는다).
3. **브라우저 콘솔에 빨간 에러가 없는지** 본다.
4. **DESIGN·VOICE와 눈에 띄게 어긋난 곳이 없는지** 스크린샷으로 한 번 본다(엉뚱한 색, 기본 글꼴, 금지선에 걸리는 문구).

통과하지 못한 기준이 있으면 고치고 그 기준을 다시 눌러본다. **같은 문제를 두 번 고쳐도 안 되면** 멈추고 Step 5-3으로 간다.

---

## Step 4 — 저장하고 기록하기

조각의 모든 확인 기준이 통과하면:

1. **SPEC.md 체크.** 해당 조각의 `- [ ]`을 `- [x]`로 바꾼다. 조각 내용은 고치지 않는다.
2. **작업 기록 한 줄.** `docs/work/LOG.md` 맨 아래에 추가한다. 파일이 없으면 아래 머리말과 함께 만든다.
   ```markdown
   # Log — {서비스 이름}

   > Vibe Studio · build-slice · 조각 완료·고침·되돌림을 시간순으로 (최신이 아래)

   - <YYYY-MM-DD> · 01-f1-first-visit 조각 2 완료 · 달라진 점: 책 카드에 '걸어서 몇 분'을 제목 위로 올림 · 다음에 할 것: 카드 정렬 기준
   ```
   - 줄 앞에는 항상 **묶음 폴더 이름**을 붙인다. build-check가 이걸로 묶음의 기록을 모은다.
   - **달라진 점** — FLOWS나 SPEC과 다르게 만든 것(사용자와 정한 것 포함). 없으면 뺀다. build-check와 userflow-generator가 이걸 보고 FLOWS에 반영한다.
   - **다음에 할 것** — 만들다 발견했지만 이 조각 밖이라 미룬 것. 없으면 뺀다.
3. **커밋.** 코드와 SPEC.md·LOG.md를 한 커밋에 담는다. 메시지는 화면 기준의 쉬운 한국어로: `01 조각 2: 홈 — 지도와 책 카드`. 커밋은 "저장 지점"이라고 부른다 — 나중에 문제가 생기면 여기로 돌아올 수 있다.

### 조각마다 짧은 보고

조각 하나를 저장할 때마다 한두 줄로만 말하고 바로 다음 조각으로 간다(허락을 기다리지 않는다): `조각 {n} 완료 — {화면에 생긴 것}. 저장 지점을 남겼어요. 다음은 "{다음 조각 이름}"이에요.` 스크린샷은 확인 중에 이미 보여줬으니 다시 늘어놓지 않는다.

### 묶음을 다 만들었으면: 개발 서버 띄우고 알려주기

마지막 조각까지 저장하면:

1. **개발 서버를 켜 둔다.** 앱을 띄운 채로 끝낸다(끄지 않는다). Claude 앱의 브라우저 창이 있으면 `.claude/launch.json`으로 띄워 앱이 떠 있게 한다. 없으면 터미널에서 백그라운드로 켜 두고(대화가 서버 때문에 멈추지 않게) 주소(Vite `http://localhost:5173`, Next.js `http://localhost:3000`)를 알려준다. 끝내기 전에 그 주소가 실제로 열리는지 한 번 확인한다.
2. **전체 보고.** 만든 조각 목록, 조각마다 확인한 기준 요약, 흉내 낸 것(SETUP 기준), 달라진 점, "다음에 할 것"을 짧게 정리한다.
3. **직접 눌러보라고 알려준다.**
   > {묶음 이름}의 조각 {개수}개를 모두 만들고, 조각마다 저장해 뒀어요. 앱을 켜 둔 상태예요 — 옆 브라우저 창(또는 {주소})에서 직접 눌러봐도 돼요. 이상한 곳이 있으면 "이상해요"라고 말해 주세요. 괜찮으면 build-check로 처음부터 끝까지 사용자처럼 써볼게요. (같은 대화보다 새 대화에서 부르면 더 꼼꼼히 봐요.)

멈춰서 끝나는 경우(두 번 고쳐도 안 됨 등)에는 서버 안내 대신, 어디까지 저장됐는지와 남은 조각, 멈춘 이유를 말하고 새 대화에서 build-slice를 다시 부르면 남은 조각부터 이어서 한다고 안내한다.

## Step 5 — 고치기 ("이상해요")

### 5-1. 무엇이 이상한지 듣기
사용자의 말에서 세 가지를 찾는다. 빠진 것만 하나씩 묻는다.
- **어디서** — 어느 화면, 무엇을 눌렀을 때
- **기대한 것** — 원래 어떻게 되길 바랐나
- **실제로 일어난 것** — 무엇이 보였나 (스크린샷이 있으면 받는다)

### 5-2. 직접 재현하고 고치기
1. 브라우저에서 사용자가 말한 대로 똑같이 해본다. 콘솔 에러가 있으면 **처음 나온 에러**를 본다.
2. 원인을 **쉬운 말로 한두 줄** 설명한다. 후보가 여럿이면 가능성 높은 순으로 2~3개.
3. **가장 작게** 고친다. 문제와 상관없는 곳은 건드리지 않는다.
4. 같은 동작을 다시 해서 고쳐졌는지 스크린샷으로 보여준다. 이미 체크된 조각 중 영향받았을 만한 확인 기준도 다시 눌러본다.
5. 커밋(`고침: 책 상세에서 요청 버튼이 안 눌리던 문제`)하고 LOG.md에 한 줄 남긴다. 고친 곳이 특정 묶음의 조각이면 그 묶음 이름을, 아니면 `고침`을 줄 앞에 붙인다(`- <YYYY-MM-DD> · 고침 · 책 상세의 요청 버튼`).

**문제가 아니라 바꾸고 싶은 거면**(예: "버튼 색이 별로예요"), 고치기 전에 그게 DESIGN·VOICE·FLOWS와 다른지 알려준다. 다르면 "이번만 바꿀까요, 아니면 DESIGN.md부터 바꿀까요?"라고 묻는다.

### 5-3. 두 번 고쳐도 안 되면
더 고치지 않는다. 같은 대화에서 계속 고칠수록 점점 더 꼬이기 쉽다.
> 두 번 고쳐봤는데 안 되네요. 마지막으로 잘 되던 저장 지점({커밋 메시지})으로 되돌리고, 다른 방법으로 다시 해볼까요?

사용자가 원하면 Step 6으로 되돌리고, 무엇이 문제였는지 LOG.md에 남긴 뒤 **새 대화에서** 다시 시도하자고 안내한다.

## Step 6 — 되돌리기

1. 최근 커밋을 **사용자가 알아볼 수 있게** 보여준다(메시지와 날짜, 최근 5개).
2. 돌아갈 지점을 사용자가 고르게 한다. 아직 저장하지 않은 변경이 있으면 "저장 안 한 변경이 사라져요"라고 먼저 알린다.
3. 되돌린 뒤 앱을 띄워 그 지점의 화면이 나오는지 확인한다.
4. 묶음 SPEC.md들의 체크가 되돌린 지점과 맞는지 보고, 안 맞으면 체크를 맞춘다. LOG.md에 "되돌림: {지점}으로"를 남긴다.

되돌리기는 git으로 한다. 이미 다른 곳에 올린(push한) 커밋을 지우는 방식(강제 push)은 쓰지 않는다.
