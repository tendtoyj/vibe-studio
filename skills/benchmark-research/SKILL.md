# Benchmark Research

기획 중인 아이디어와 닮은 **경쟁 서비스·참고 프로덕트**를 조사해, 우리가 무엇을 다르게 가져갈지 결정하기 위한 리서치다. 깊은 시장 분석이 목적이 아니다 — 바이브 코딩으로 빠르게 만들 신규 서비스가 **어디에 자리 잡고, 무엇으로 차별화할지**를 잡는 가벼운 리서치다.

이 스킬은 Vibe Studio 기획 플로우의 **두 번째 단계**다. `docs/PRODUCT.md`를 입력으로 받고, `docs/benchmark.md`(+ `docs/images/`)를 산출한 뒤, 결론만 PRODUCT.md의 포지셔닝 칸에 올린다.

## 입력 / 산출물

- **입력:** `docs/PRODUCT.md` (brainstorming-idea 산출물). 없으면 "먼저 brainstorming-idea로 아이디어를 잡아주세요"라고 안내하거나, 사용자에게 직접 컨셉을 물어 진행한다.
- **산출물:**
  - `docs/benchmark.md` + 핵심 경쟁 화면 캡처 `docs/images/` — 리서치 원문(근거 자료).
  - `docs/benchmark.html` — benchmark.md를 보기 좋게 그린 리포트.
  - `docs/PRODUCT.md`의 `## 포지셔닝` 섹션 — 차별 프레이밍 요약 3~5줄.
  - `docs/DECISIONS.md`에 고른 포지셔닝 한 줄.
- 별도의 리서치 메모리 폴더는 만들지 않는다.

---

## 원칙

- **깊이보다 방향.** 경쟁사 5개를 완벽 분석하는 게 아니라, 3~5개를 보고 **우리의 빈틈(차별 지점)** 을 찾는 게 목표다.
- **1차 정보를 본다.** 검색 스니펫만 믿지 말고, 핵심 후보는 공식 사이트를 사용 가능한 웹/브라우징 도구로 직접 확인한다.
- **출처는 반드시 남긴다.** 모든 주장과 이미지에 출처 URL을 붙인다. 모르면 모른다고 쓰고 추측으로 빈칸을 메우지 않는다.
- 기본 언어는 한국어. 표의 컬럼명은 영어로 둬도 좋지만 본문·설명은 한국어로 쓴다.

## 작업 흐름

### 1. PRODUCT.md를 읽고 검색 축을 정한다 — "어디서 무엇을 검색할 것인가"

`docs/PRODUCT.md`의 한 줄 컨셉·핵심 솔루션·타깃을 읽고, **무엇을 찾을지** 먼저 정한다. 막연히 "비슷한 앱"을 검색하지 말고, 다음 세 축으로 나눠 검색어를 설계한다:

- **직접 경쟁 (Direct):** 같은 문제를 같은 방식으로 푸는 서비스. ("OO 기록 앱", "OO 추천 서비스")
- **간접 경쟁 / 대체재 (Indirect):** 같은 문제를 다른 방식으로 푸는 것. 사용자가 지금 대신 쓰는 것(엑셀, 메모앱, 오프라인 방법 등).
- **참고 레퍼런스 (Reference):** 도메인이 달라도 UX·기능·플로우가 배울 만한 서비스.

각 축마다 검색어를 1~2개씩 만들어, 사용 가능한 웹 검색 도구를 **여러 각도로 3~5회** 쓴다. (검색 횟수 기준이다. 다음 단계에서 공식 사이트를 직접 읽는 건 따로 센다.) 한 번의 검색은 한 가지 프레임만 주므로 각도를 바꿔야 빈틈이 메워진다. 영어 검색어도 함께 쓰면 글로벌 레퍼런스가 잡힌다.

### 2. 후보를 추리고 1차 출처를 확인한다

검색 결과에서 직접 경쟁 3~5개 + 간접/참고 2~3개를 추린다. 핵심 후보는 공식 사이트·소개 페이지를 **직접 읽어** 포지셔닝·핵심 기능·가격·타깃을 정확히 파악한다.

그리고 직접 경쟁 중 **우리와 가장 가까운 1~2개를 "핵심 경쟁"으로 고른다.** 고른 이유를 한 줄로 사용자에게 알려주고, 따로 답을 기다리지 않고 캡처로 넘어간다(사용자가 다른 서비스를 원하면 그때 바꾼다).

### 3. 핵심 경쟁 화면을 캡처한다 — "정보를 어떻게 가공할 것인가" (1)

핵심 경쟁 1~2개의 **실제 화면을 브라우저로 직접 열어 캡처**한다. 다른 사이트에 올라온 이미지 URL을 받아 대신하지 않는다 — 지금 서비스가 실제로 어떻게 생겼는지가 근거여야 한다.

- **무엇을:** 서비스마다 메인(랜딩) 화면 1장이 기본. 로그인 없이 볼 수 있는 핵심 기능 화면이 **별도 URL로** 있으면 1장 더(URL로 바로 열 수 없는 화면은 찍지 않는다). 첫 화면(뷰포트) 기준으로 찍는다.
- **크기:** `docs/PRODUCT.md`의 기준 뷰포트에 맞춘다. 모바일 우선이면 390×844, 데스크톱 우선이면 1440×900.
- **도구:** 화면을 파일로 저장할 수 있는 브라우저 도구를 쓴다.
  1. Playwright 계열 브라우저 MCP가 있으면 그것으로 열고 스크린샷을 파일로 저장한다.
  2. 없으면 셸에서 컴퓨터에 설치된 크롬으로 찍는다:
     ```bash
     npx -y playwright screenshot --channel chrome --viewport-size=<가로>,<세로> --wait-for-timeout=3000 "<URL>" docs/images/<파일>.png
     ```
     `<가로>,<세로>`는 위 "크기"대로(모바일 우선이면 `390,844`). `--wait-for-timeout=3000`은 페이지 애니메이션이 끝난 뒤 찍기 위한 대기다.
     크롬이 없어 실패하면 `npx playwright install chromium`으로 브라우저를 받아야 한다. 용량이 큰 다운로드(100MB 이상)이므로 **사용자에게 먼저 묻고**, 허락하면 받은 뒤 `--channel chrome` 없이 다시 찍는다.
  3. 화면을 보여주기만 하고 파일로 저장할 수 없는 도구뿐이면, 화면을 보고 관찰만 메모하고 "캡처 파일 없음"으로 적는다.
  4. 셋 다 안 되면 사용자에게 알리고 캡처 없이 진행한다. 캡처가 있는 척하지 않는다.
- **파일 이름:** `docs/images/{서비스 영문 이름}-{화면}.png` (예: `daangn-home.png`, `daangn-search.png`). 영문 이름이 없으면 도메인 앞부분을 쓴다(예: `woodo.kr` → `woodo`). 화면은 `home`, `search`, `pricing`처럼 짧은 영어 단어로. `docs/images/`가 없으면 만든다.
- **찍기 전:** 쿠키·광고 팝업은 닫거나 필수 항목만 남기고 거절한다. 로그인·회원가입이 필요한 화면은 찍지 않고, 계정을 만들지 않는다.
- **찍은 뒤:** 저장한 이미지를 직접 열어 확인한다. 빈 화면·에러 페이지·팝업에 가린 화면, 애니메이션이 덜 끝난 화면이면 대기 시간을 늘려 다시 찍는다. 다시 찍어도 레이아웃이 겹치거나 깨져 보이면 그게 그 사이트의 실제 모습이므로 그대로 두고 관찰에 적는다. 그리고 **무엇이 인상적인지**(레이아웃, 핵심 동선, 카피, 분위기)를 메모해 둔다. 이 메모가 benchmark.md의 "화면 캡처"와 "관찰"로 들어간다. 모든 캡처는 출처 URL과 캡처일을 함께 기록한다.

### 4. benchmark.md를 작성한다 — "정보를 어떻게 가공할 것인가" (2)

조사한 내용을 아래 구조로 정리한다. 핵심은 **나열이 아니라 비교**다. 표로 한눈에 비교하고, 마지막에 반드시 **우리의 차별 프레이밍**을 도출한다 — 이 리서치의 진짜 목적이다.

여기까지가 **기본 리서치**다. benchmark.md 초안이 만들어지면, 보고 전에 심화 여부를 묻는다.

### 4.5 심화 리서치 (선택)

기본 조사는 일반 웹 검색/페이지 확인 기준이라 사이트 문구·가격이 부정확하거나, 실제 화면을 못 볼 수 있다. 더 깊이 파고 싶은지 사용자에게 묻는다:

> "여기까지가 기본 조사예요. 경쟁사 사이트를 더 깊이 파볼까요? 사이트 문구·가격을 정확히 긁어오거나(Firecrawl), 나머지 경쟁사 화면까지 캡처해서 디자인을 더 보는(Playwright) 심화 조사예요. 시간이 더 걸립니다."

**사용자가 원하면**, 필요한 MCP나 브라우저 도구가 연결돼 있는지 먼저 확인한다. 그리고 해당 도구로 보강한다:

- **Firecrawl 계열 스크래퍼:** 경쟁사 홈/가격 페이지를 스크랩해 **정확한 헤드라인·서브카피·CTA·가격 모델**을 가져온다. → `핵심 기능 비교`·`관찰`을 추측이 아니라 실측으로 채운다.
- **Playwright/Browser 계열 브라우저 도구:** 기본 단계에서 찍은 핵심 경쟁 1~2개 외에 **나머지 서비스와 더 많은 화면**(가격 페이지, 주요 기능 화면 등)까지 3단계와 같은 방식으로 캡처하고, 색·레이아웃·핵심 동선 같은 **디자인 관찰**을 추가한다.

둘 다 할 수도, 하나만 할 수도 있다. 심화로 채운 내용은 benchmark.md의 **기존 섹션을 보강**하고, 해당 항목에 `(심화)` 표시를 단다(아래 템플릿 참고).

**안전장치:**
- 필요한 MCP가 연결돼 있지 **않으면**, 그 사실을 사용자에게 알리고 **기본 리서치 결과로 마무리**한다. 없는 도구를 있는 척하거나 결과를 지어내지 않는다.
- 심화를 건너뛰어도 benchmark.md는 그 자체로 **완결**이다. 심화는 어디까지나 부가다.
- 스크랩·캡처한 정보도 **출처 URL을 반드시 남긴다.**

### 5. 검증하고 보고한다

benchmark.html, PRODUCT.md 포지셔닝 칸(과 PRODUCT.html), DECISIONS.md까지 반영했는지 확인한 뒤(아래 "benchmark.html 만들기", "PRODUCT.md에 결론 올리기"), 폴더 구조를 확인하고(`find docs -type f`) 사용자에게 짧게 보고한다: 만든 문서 경로, 비교한 서비스 수, 캡처한 화면 수(캡처 못 했으면 그 이유), **심화 리서치 수행 여부**, 그리고 **우리가 잡은 차별 프레이밍 한 줄**. 확인이 더 필요한 불확실한 정보(2차 출처에만 있는 가격 등)는 따로 짚는다.

## 산출물 구조 — docs/benchmark.md (필수 산출물)


## benchmark.html 만들기

심화 리서치 여부까지 정리돼 benchmark.md가 최종 저장되면, `<스킬경로>/../../assets/REPORT.md`의 절차대로 `docs/benchmark.html`을 만든다. html은 대화 내용이 아니라 **저장된 benchmark.md 파일만** 보고 채운다. 새 html이 생겼으므로 `docs/`의 다른 html 사이드바도 REPORT.md 규칙대로 갱신한다.

**순서:** benchmark.md 저장 → benchmark.html 생성 → 아래 "PRODUCT.md에 결론 올리기"(PRODUCT.md → PRODUCT.html). benchmark.html을 먼저 만들어야 PRODUCT.html의 포지셔닝 근거가 benchmark.html로 링크된다. PRODUCT.html은 곧 통째로 다시 만들어지므로, 사이드바 갱신 때 PRODUCT.html은 건너뛰어도 된다.

## PRODUCT.md에 결론 올리기

심화 리서치 여부까지 정리돼 benchmark.md가 최종 저장된 뒤, **차별 프레이밍의 결론만** `docs/PRODUCT.md`의 `## 포지셔닝` 섹션에 채운다. 리서치 원문(경쟁사 표·가격·이미지·출처)은 옮기지 않는다 — PRODUCT.md는 에이전트가 매번 읽는 짧은 파일이고, 근거는 benchmark.md에 남는다.

```markdown
## 포지셔닝
- **우리의 자리:** <한 문장>
- **빈틈/기회:** <경쟁이 못 채운 지점>
- **차별 포인트:** <우리가 다르게 가져갈 핵심 1~2개>
- 근거: docs/benchmark.md (<YYYY-MM-DD> 조사)
```

- 쓰기 전에 포지셔닝 네 줄을 사용자에게 보여주고 **내용을 확인받는다**(저장 여부가 아니라 내용). 이때 리서치에서 보인 **다른 자리 1개**도 한 줄로 같이 보여주면("이쪽으로 갈 수도 있는데, 이런 이유로 위를 추천해요") 사용자의 선택이 분명해지고 DECISIONS.md의 "버린 방향"이 남는다. 사용자가 확인한 내용이 DECISIONS.md에 적을 근거가 된다.
- 섹션이 주석만 있는 빈 상태면 주석을 지우고 채운다. 이미 내용이 있으면(재조사) 무엇이 바뀌는지 보여주고 확인받은 뒤 고친다. 포지셔닝이 바뀌었으면 DECISIONS.md에 새 줄을 추가하고 기존 포지셔닝 줄의 상태를 `번복 → D-00N`으로 고친다.
- PRODUCT.md에 `## 포지셔닝` 섹션이 없으면 `## 플랫폼` 바로 앞에 새로 만든다.
- PRODUCT.md의 다른 섹션은 건드리지 않는다.
- `docs/PRODUCT.html`이 있으면 `<스킬경로>/../../assets/REPORT.md`의 절차대로 다시 만든다(고친 PRODUCT.md 파일만 보고 채운다).

그리고 사용자가 확인한 포지셔닝을 `docs/DECISIONS.md`에 한 줄 추가한다. 파일이 없으면 헤더째 만든다. 형식:

```markdown
| ID | 날짜 | 단계 | 결정 | 이유 · 버린 대안 | 상태 |
|----|------|------|------|-----------------|------|
| D-00N | <YYYY-MM-DD> | benchmark-research | 포지셔닝: <한 문장> | <사용자에게 보여주고 확인받은 근거> · 버린 방향: <검토했지만 안 간 자리> | 유효 |
```

사용자가 고르거나 확인한 것만 적고(이유도 대화에서 나온 것만, 없으면 `—`. 버린 대안이 없으면 그 부분은 뺀다), ID는 이어서 매기며, 기존 줄은 지우지 않는다(바뀌면 새 줄 추가 + 기존 줄 상태를 `번복 → D-00N`으로).

저장 후 다음 단계를 안내한다:

> benchmark.md 저장 완료, 포지셔닝은 PRODUCT.md에도 올려뒀어요. 브라우저로 `docs/benchmark.html`을 열면 경쟁사 비교와 화면 캡처를 한눈에 볼 수 있어요(`docs/PRODUCT.html`도 새로 그렸어요). 다음은 **brand-voice**로 서비스 이름을 확정하고 브랜드의 말투와 성격을 잡아요.

## 사실성 원칙
- 가격·수치·고유명사는 1차 출처 기준. 2차 매체에만 있으면 "별도 확인 필요"로 표기한다.
- 1차 출처 = 서비스가 직접 운영하는 곳(공식 사이트, 앱스토어·플레이스토어의 공식 앱 페이지, 공식 블로그). 기사·리뷰·Product Hunt 같은 곳은 2차다.
- 출처 없는 주장은 쓰지 않는다.
- 모르면 모른다고 쓴다. 빈칸을 그럴듯한 추측으로 메우지 않는다.
