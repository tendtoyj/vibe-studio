Vibe Studio의 만들기 고리(build-spec → build-slice → build-check)에서 플로우를 하나 새로 만들 때마다 여는 단계다.

# Build Spec

기획 문서를 **이번에 만들 조각과 조각별 확인 방법**으로 옮겨 `docs/work/`에 **작업 묶음** 하나로 만든다.

- `docs/work/SETUP.md` — 모든 묶음이 같이 쓰는 것(스택·데이터·흉내만 낼 것·이번엔 안 함). 처음 한 번 만들고, 바뀔 때만 고친다.
- `docs/work/{NN-이름}/SPEC.md` — 묶음 하나의 목표와 조각 체크리스트. 부를 때마다 하나씩 생긴다. 폴더 이름 규칙은 LAYOUT.md의 "작업 묶음".

묶음은 플로우 하나와 같을 때가 많지만 꼭 그렇지는 않다. F1을 진짜로 동작하게 하는 것, 프로토타입에서 Next.js로 옮기는 것, F1·F2에 걸친 로그인을 진짜로 붙이는 것도 각각 묶음 하나다.

SPEC.md는 기획을 다시 요약하는 문서가 아니다. 무엇을·왜는 PRODUCT.md, 화면과 흐름은 FLOWS.md, 모습과 말투는 DESIGN.md·VOICE.md에 이미 있다. SETUP.md와 SPEC.md에는 **만들 때만 필요한 결정**(어떤 틀로, 무엇을 흉내 내고, 어떤 순서로, 다 됐는지 어떻게 아는지)만 적고, 나머지는 FLOWS의 단계 번호로 연결만 건다.

만들기는 한 번에 끝나지 않는다. 플로우 하나를 그리고, 쪼개고, 만들고, 써보고, 바뀐 걸 반영한 뒤 다음 플로우로 넘어가는 **고리를 계속 돈다.** 이 스킬은 그 고리에서 플로우를 하나 새로 시작할 때마다 부른다(처음 한 번만 쓰는 스킬이 아니다):

```
┌→ userflow-generator (플로우 그리기 · 바뀐 것 반영)
│      ↓
│  build-spec   (그 플로우를 조각으로 쪼개기)
│      ↓
│  build-slice  (조각 하나씩 만들기 · 반복)
│      ↓
│  build-check  (플로우를 처음부터 끝까지 써보기)
└──────┘
```

중간에 정해둔 것(스택, 흉내 낼 것)이 바뀌어야 할 때도 이 스킬을 다시 부른다.

## 기본 스택

스택은 아래 셋 중에서만 고른다.

| 이름 | 스택 | 언제 |
|---|---|---|
| **프로토타입** | Vite + React + TypeScript + Tailwind CSS | 화면을 눌러보며 흐름을 확인하는 게 목표일 때. 기본값 |
| **실제 기능** | Next.js (App Router) + TypeScript + Tailwind CSS | 비밀 키가 필요한 기능을 진짜로 붙이거나, 실제 사람들이 쓰게 할 때 |
| **진짜 저장소** | Supabase (위 둘 중 하나에 더함) | 여러 사람이 실제 데이터를 주고받아야 할 때. 첫 버전에선 쓰지 않고 나중 조각으로 미룬다 |

## 입력 / 산출물

docs 폴더 구조는 `<스킬경로>/../../assets/LAYOUT.md`를 따른다.

- **입력:**
  - `docs/FLOWS.md` — **필수.** 상태가 `기획 완료`(또는 `UI 구현`)인 플로우가 하나 이상 있어야 한다. 없으면 "먼저 userflow-generator로 플로우를 하나 그려 주세요"라고 안내하고 멈춘다.
  - `docs/PRODUCT.md` — 핵심 기능, 플랫폼. 스택을 정할 때 읽는다.
  - `docs/DESIGN.md` — **frontmatter의 `runtime_deps`(아이콘·글꼴 라이브러리)만** 읽는다. 시각 내용은 build-slice가 읽는다.
  - `docs/DECISIONS.md` — 이미 정한 것. 여기 있는 건 다시 묻지 않는다.
  - `docs/work/` — 있으면 SETUP.md와 묶음들의 진행(체크된 조각 수)을 읽는다.
  - 프로젝트 코드 — `package.json`이 있으면 이미 스택이 정해진 것이다. 스택을 묻지 않고 코드를 따른다.
- **산출물:**
  - `docs/work/SETUP.md` (처음 한 번, 이후엔 바뀐 줄만)
  - `docs/work/{NN-이름}/SPEC.md` (부를 때마다 묶음 하나)
  - `docs/DECISIONS.md`에 이 단계의 결정.
- **하지 않는 것:** 코드 작성, 프로젝트 생성, 패키지 설치, FLOWS.md 수정. 프로젝트를 실제로 만드는 건 build-slice의 첫 조각이다.

### 플로우 상태 (FLOWS.md와 같은 이름)

`후보` → `기획 완료` → `UI 구현` → `기능 구현`

- `기획 완료` — FLOWS.md에 화면·상태·예외까지 그려졌다. **이 스킬이 조각으로 쪼개는 출발점.**
- `UI 구현` — 화면과 화면 이동은 있지만 데이터·로그인·외부 연동이 가짜다. **흉내를 쓰는 조각을 다 만들면 여기에 닿는다.**
- `기능 구현` — 목표 순간까지 실제로 동작한다. **흉내를 진짜로 바꾸는 조각을 다 만들면 여기에 닿는다.**

플로우를 다루는 묶음의 SPEC.md는 이 중 어디를 향하는지 `목표:`로 적는다. 상태를 실제로 바꾸는 건 이 스킬이 아니다(userflow-generator가 코드를 읽고 정한다).

## 원칙

- **다시 쓰지 않고 연결한다.** 조각에는 `(F1 ③④)`처럼 FLOWS의 단계 번호만 건다. 화면 요소·문구·상태를 SPEC에 옮겨 적지 않는다.
- **흉내 낼 수 있으면 흉내 낸다.** 첫 버전의 목표는 흐름을 처음부터 끝까지 눌러보는 것이다. 로그인·위치·지도·알림·결제·외부 서비스는 먼저 가짜로 동작하게 하고, 진짜로 붙이는 건 나중 조각으로 미룬다.
- **확인 기준은 화면에서 보이는 문장으로 쓴다.** "~하면 ~가 보인다" 꼴로, 사람이 브라우저에서 눌러보고 맞는지 알 수 있어야 한다. 코드를 읽어야 아는 기준("상태가 저장된다")은 쓰지 않는다. 사람이 화면으로 확인할 수 없으면 에이전트도 확인할 수 없다.
- **조각마다 앱이 켜지는 상태로 끝난다.** 반쯤 만든 화면이 다음 조각을 기다리는 쪼개기는 하지 않는다.
- **묻는 건 한 번 실행에 최대 3개.** 스택(처음 한 번)과 정말 갈리는 것만 묻고, 나머지는 추천대로 두고 "이건 이렇게 했어요"로 한 번에 보여준다.

**대화 스타일:** 한국어 기본, 친근한 톤("~할까요", "~해볼게요"). 사용자는 개발을 모른다고 가정한다. 프레임워크·라이브러리 같은 말은 처음 한 번 쉬운 말로 풀어 쓴다. 질문은 한 번에 하나.

## Step 0 — 모드 판단

- **`docs/work/SETUP.md`가 없으면 → 처음 실행.** Step 1(정해둘 것) → Step 2(플로우 쪼개기) → Step 3(저장).
- **있으면 →** 정해둔 것과 묶음별 진행(묶음 이름, 체크된 조각 수)을 짧게 보여주고 무엇을 할지 묻는다. 체크 안 된 조각이 남은 묶음이 있으면 "{묶음}이 아직 {n}개 남았어요. 새 묶음을 만들어도 build-slice는 남은 것부터 해요"라고 함께 알린다.
  - **다음 플로우 준비** — FLOWS에서 `기획 완료`인데, `관련 플로우`에 그 플로우가 있고 목표가 `UI 구현`인 묶음이 아직 없는 플로우. 여러 개면 FLOWS 순서대로 추천한다. 없으면 "다음 플로우를 먼저 userflow-generator로 그려 주세요"라고 안내한다. → Step 2 → Step 3.
  - **기능 구현으로 올리기** — FLOWS에서 `UI 구현`인 플로우의 흉내 낸 부분을 진짜로 바꾼다. → Step 2-5 → Step 3.
  - **정해둔 것 바꾸기** — 예: 프로토타입에서 실제 기능으로 옮기기. → Step 1의 해당 부분 → Step 2-6 → Step 3. 기능 구현으로 올리려는데 스택이 프로토타입(Vite)이고 진짜로 바꿀 것 중 서버가 필요한 게 있으면(키, 로그인, 데이터 저장) 이걸 먼저 한다.
  - **그 밖의 작업** — 여러 화면을 한꺼번에 다듬기, 배포하기처럼 플로우 하나에 묶이지 않는 일. → Step 2-7 → Step 3.
  - 사용자의 말에 할 일이 이미 들어 있으면 묻지 않고 바로 진행한다.

## Step 1 — 정해둘 것 (처음 한 번)

### 1-1. 스택 고르기

**코드가 이미 있으면** `package.json`에서 스택을 읽어 그대로 적고 넘어간다.

**코드가 없으면** PRODUCT.md의 핵심 기능과 FLOWS의 **첫 버전 범위**를 읽고, 아래 조건에 걸리는지 본다.

| 조건 | 추천 |
|---|---|
| 첫 버전의 핵심 가치에 **비밀 키가 꼭 필요한 기능**이 있다. 예: AI로 요약·추천·생성하는 게 서비스의 핵심, 유료 API 키가 필요한 외부 서비스 | 실제 기능 (Next.js) |
| 사용자가 "실제로 사람들이 쓰게 하고 싶다", "배포해서 친구들이 써보게 하고 싶다"고 했다 | 실제 기능 (Next.js) |
| 그 밖의 경우. 로그인·위치·지도·여러 사람 사이 주고받기는 흉내로 충분하다 | 프로토타입 (Vite) |

추천이 정해지면 아래처럼 **두 선택지를 설명하고 고르게 한다.** 문장은 서비스에 맞게 다듬되 세 가지 요점(Vite는 화면용이라 덜 까다롭지만 키를 숨길 곳이 없다 / Next.js는 까다롭지만 진짜 기능을 붙일 수 있다 / 나중에 옮기면 흉내 낸 부분의 보안을 다시 손봐야 한다)은 빼지 않는다.

> 만들기 전에 하나만 정할게요. 앱을 어떤 틀로 만들지예요.
>
> **Vite** — 화면을 빠르게 만들어 보는 틀이에요. 눌러보고 넘겨보는 프로토타입을 만들기 좋고 덜 까다로워요. 대신 모든 코드가 사용하는 사람의 브라우저로 그대로 전달돼서, 비밀번호나 API 키처럼 숨겨야 할 걸 둘 곳이 없어요. 그래서 로그인·AI·결제 같은 진짜 기능은 흉내만 내요.
>
> **Next.js** — 조금 까다로워요. 대신 브라우저에 보이지 않는 '서버' 공간이 있어서, 키를 숨기고 진짜 기능을 붙일 수 있어요.
>
> Vite로 시작했다가 나중에 Next.js로 옮길 수도 있어요. 화면은 대부분 그대로 가져가지만, 흉내 냈던 부분(로그인, 데이터 저장, 키가 필요한 기능)을 서버 쪽으로 옮기면서 **보안을 다시 손봐야 해요.**
>
> {서비스 이름}의 첫 버전은 {이유 한 줄}이라서 **{추천}**을 추천해요. 어떻게 할까요?

아이콘·글꼴은 DESIGN.md의 `runtime_deps`를 그대로 스택에 적는다. React용 라이브러리라 두 선택지 모두 그대로 쓸 수 있다. `runtime_deps`가 없으면 적지 않는다.

### 1-2. 데이터

첫 버전은 스택과 상관없이 **가짜 데이터를 브라우저에 저장**한다(새로고침해도 남게). 가짜 데이터의 양은 화면이 그럴듯해 보일 만큼만 정한다(예: 이웃 5명, 책 20권). 진짜 저장소(Supabase)는 나중 조각이다.

### 1-3. 흉내만 낼 것

FLOWS의 첫 버전 범위에서 외부에 기대는 요소를 찾아, 각각 **어떻게 흉내 낼지 한 줄**로 정한다.

| 흔한 요소 | 흉내 내는 법 (예) |
|---|---|
| 로그인·문자 인증 | 아무 번호나 넣으면 통과 |
| 위치 권한·현재 위치 | 고정된 동네 하나로 시작, 허용/거절 둘 다 눌러볼 수 있게 |
| 지도 | 지도 모양 그림 위에 점 |
| 알림·문자 발송 | 화면 안 안내 문구로 대신 |
| 결제 | [결제하기]를 누르면 바로 완료 화면 |
| AI 기능 (프로토타입일 때) | 미리 써둔 그럴듯한 결과를 보여줌 |
| 여러 사람 사이 주고받기 | 상대방 행동을 가짜 데이터로 미리 넣어둠 |

**프로토타입(Vite)을 골랐으면** 이 목록에서 나중에 Next.js로 옮길 때 서버로 가야 하는 것(키가 필요한 것, 로그인, 데이터 저장)을 골라 SETUP.md의 "옮길 때 다시 볼 것"에 적는다. 1-1에서 말한 "보안을 다시 손봐야 하는 곳"이 바로 이 목록이다.

### 1-4. 이번엔 안 함

FLOWS 첫 버전 범위의 **나중에**, PRODUCT.md의 확장 아이디어, 1-3에서 진짜로 붙이는 걸 미룬 것을 모은다. build-slice는 이 목록에 있는 걸 만들지 않는다.

## Step 2 — 플로우를 조각으로 쪼개기

### 2-1. 대상 플로우
처음 실행이면 FLOWS의 `기획 완료` 플로우 중 첫 번째(보통 F1). 사용자가 다른 플로우를 말하면 그걸 한다. 이 묶음의 목표는 `UI 구현`이다.

### 2-2. 조각 초안
플로우의 단계를 순서대로 따라가며 **조각 3~6개**로 묶는다.

- **한 조각 = 직접 눌러볼 수 있는 화면 1~2개.** 주 행동 하나로 금방 넘어가는 화면들은 묶는다(소개 → 동네 설정).
- **첫 플로우의 조각 1은 항상 "프로젝트 준비 + 첫 화면이 가짜 데이터로 보이기"다.** 한 번에 다 만들지 못해도 첫 세션에서 눈에 보이는 화면 하나는 남게 하기 위해서다.
- 각 조각에는 이름과 FLOWS 단계 번호만 붙인다.

### 2-3. 확인 기준 붙이기
조각마다 **2~4줄**. FLOWS에서 가져온다.

- **주 행동** — 잘 풀리는 길 하나: "[우리 동네 책장 보기]를 누르면 동네 설정이 나온다"
- **상태** — 빈·오류 상태 중 이 조각에서 눌러서 만들어 볼 수 있는 것: "책이 0권이면 '아직 근처에 꽂힌 책이 없어요'가 보인다". 로딩 상태처럼 순간 지나가 확인하기 어려운 건 넣지 않는다.
- **예외** — FLOWS 예외표에서 이 조각에 해당하는 것 중 중요한 것 하나
- **흉내 낸 것** — 이 조각에 흉내 낸 요소가 있으면 그게 동작하는지: "아무 번호나 넣으면 다음으로 넘어간다"

문구를 확인할 때는 FLOWS에 적힌 문구를 그대로 쓴다. `(임시)` 표시는 옮기지 않는다.

### 2-4. 보여주고 확인
조각 목록을 한 번에 보여준다. 갈리는 것(조각 순서, 이 플로우에서 흉내 낼지 진짜로 할지)만 묻고, 나머지는 "이건 이렇게 했어요"로 모아 보여준다.

### 2-5. 기능 구현으로 올리기
`UI 구현`인 플로우에서 흉내 낸 부분을 진짜로 바꾸는 조각을 만든다. **목표가 `기능 구현`인 새 묶음**을 만든다(예: `02-f1-real`). UI 구현 때의 묶음은 그대로 둔다.

- 진짜로 바꿀 것이 여러 플로우에 걸치면(예: F1·F2가 같이 쓰는 로그인) 플로우마다 나누지 말고 묶음 하나로 만든다. 폴더 이름에 플로우 ID를 붙이지 않고(`04-real-login`), `관련 플로우:`에 모두 적는다.

- SETUP.md의 "흉내만 낼 것" 중 이 플로우에 걸린 것을 고른다. 하나를 진짜로 바꾸는 게 **조각 하나**다.
- 진짜 저장소(Supabase)를 처음 쓰는 조각이면, 그 조각에 "다른 사람 계정으로는 내 데이터가 보이지 않는다"는 확인을 꼭 넣는다.
- 확인 기준은 흉내와 진짜의 차이가 화면에서 드러나게 쓴다: "새로고침하거나 다른 기기에서 열어도 요청이 남아 있다", "틀린 인증번호를 넣으면 넘어가지 않는다".
- 모든 흉내를 한 번에 바꿀 필요는 없다. 사용자가 고른 것만 하고, 남은 건 "이번엔 안 함"에 그대로 둔다.

### 2-6. 스택 옮기기
SETUP.md의 스택을 바꿨으면 **옮기기 묶음**을 만든다(예: `03-move-to-nextjs`). 목표는 `옮기기`, 관련 플로우는 지금까지 만든 플로우 전부.

- 조각 1은 항상 "화면 그대로 새 틀로 옮기기"다. 확인 기준: 지금까지 체크된 모든 조각의 확인 기준을 다시 눌러봐서 통과한다 · 화면 모습이 옮기기 전과 같다.
- SETUP.md "옮길 때 다시 볼 것"의 항목마다 **서버 쪽에 자리를 만드는 조각**을 하나씩 둔다. 이번에 진짜로 붙이지 않으면 흉내는 그대로 두고, 확인 기준은 "브라우저 코드에 비밀 값이 없다"처럼 쓴다.

### 2-7. 그 밖의 작업 묶음
플로우 하나에 묶이지 않는 일도 같은 원칙으로 만든다: 조각 3~6개, 조각마다 앱이 켜지는 상태로 끝남, 확인 기준은 화면에서 보이는 문장. 목표는 한 줄로 그 일이 끝났을 때 보이는 모습을 쓴다(예: `목표: 친구가 주소로 들어와 F1을 끝까지 쓸 수 있다`). 관련 플로우가 없으면 `—`.

## Step 3 — 저장 (필수 산출물)

**이 스킬의 최종 산출물은 항상 `docs/work/` 아래의 파일이다.** 채팅에만 보여주고 끝내지 않고, "저장할까요?"라고 묻지 않는다. 날짜는 시스템이 준 오늘 날짜를 쓴다.

- **SETUP.md** — 처음 실행이면 아래 구조로 새로 쓴다. 이미 있으면 **바뀐 줄만 고친다.** 사람이 직접 적은 내용은 건드리지 않는다.
- **묶음 폴더** — 순번과 이름을 LAYOUT.md 규칙대로 정해 새 폴더를 만들고 `SPEC.md`를 쓴다. 이미 있는 묶음의 SPEC.md는 고치지 않는다(체크 표시는 build-slice가 한다).
- **git에 저장되는지 확인** — 처음 실행이면 저장한 뒤 `git check-ignore -v docs/work/SETUP.md`로 확인한다(git 저장소가 아니면 건너뛴다). 무시되고 있으면 `.gitignore`의 어느 줄 때문인지 보여주고, 그 줄을 고칠지 묻는다. 무시된 채로 두면 체크 표시와 작업 기록이 저장 지점(커밋)에 들어가지 않는다.

### docs/work/SETUP.md

~~~markdown
# Setup — {서비스 이름}

> Vibe Studio · build-spec · 모든 작업 묶음이 같이 쓰는 것
> 작성일: <YYYY-MM-DD> · 최종 수정일: <YYYY-MM-DD>
> 기반: docs/PRODUCT.md, docs/FLOWS.md, docs/DESIGN.md, docs/DECISIONS.md

- **스택:** 프로토타입 — Vite + React + TypeScript + Tailwind CSS · 아이콘 Phosphor(`@phosphor-icons/react`) · 글꼴 Pretendard
  - 이유: 첫 버전에 비밀 키가 필요한 기능이 없음
- **데이터:** 가짜 데이터(이웃 5명, 책 20권)를 브라우저에 저장. 진짜 저장소는 나중에
- **흉내만 낼 것:**
  - 로그인 — 아무 번호나 넣으면 통과
  - 위치 — 고정된 동네 하나, 허용/거절 둘 다 눌러볼 수 있게
  - 지도 — 지도 모양 그림 위에 책장 점
- **이번엔 안 함:** 실제 문자 인증, 진짜 저장소, 빌려준 권수 표시, 동네 독서모임
- **옮길 때 다시 볼 것** (Next.js로 옮기면 서버로 가야 하는 것): 로그인, 대여 요청 저장
~~~

`옮길 때 다시 볼 것`은 프로토타입일 때만 둔다. 흉내를 진짜로 바꾼 묶음을 다 만들면 그 줄을 "흉내만 낼 것"에서 지운다(다음에 build-spec을 부를 때 묶음 체크 상태를 보고 정리한다).

### docs/work/01-f1-first-visit/SPEC.md

~~~markdown
# 01 · F1 첫 대여 요청

> Vibe Studio · build-spec · 작성일: <YYYY-MM-DD>
> 목표: UI 구현 · 관련 플로우: F1 · 조각 3개
> 정해둔 것: ../SETUP.md

- [ ] **1. 프로젝트 준비 + 소개 → 동네 설정** (F1 ①②)
  - 확인: 첫 화면에 "돈도 택배도 없이, 옆집 책장에서 한 권 빌려보세요."가 보인다
  - 확인: [우리 동네 책장 보기] → 동네 설정이 나온다
  - 확인: 위치를 거절하면 동네 직접 고르기로 넘어간다
- [ ] **2. 홈 — 지도와 책 카드** (F1 ③)
  - 확인: 지도 아래 책 카드가 보이고, 카드를 누르면 책 상세로 간다
  - 확인: 책이 0권이면 "아직 근처에 꽂힌 책이 없어요."가 보인다
- [ ] **3. 책 상세에서 요청 보내기** (F1 ④⑤⑥)
  - 확인: 받을 곳을 고르고 [요청 보내기] → 로그인 시트 → 아무 번호나 넣으면 요청 완료 화면
  - 확인: 같은 책에 다시 요청하면 "이미 요청을 보냈어요."가 보인다
  - 확인: 로그인 시트를 닫으면 쓰던 메모가 그대로 있다
~~~

나중에 F1을 기능 구현으로 올리면 새 묶음이 생긴다:

~~~markdown
# 02 · F1 첫 대여 요청 — 진짜로 동작하게

> Vibe Studio · build-spec · 작성일: <YYYY-MM-DD>
> 목표: 기능 구현 · 관련 플로우: F1 · 조각 2개
> 정해둔 것: ../SETUP.md

- [ ] **1. 대여 요청을 진짜 저장소에 저장** (F1 ④⑥)
  - 확인: 요청을 보내고 새로고침하거나 다른 기기에서 열어도 요청이 남아 있다
  - 확인: 다른 사람 계정으로는 내 요청이 보이지 않는다
- [ ] **2. 휴대폰 번호 로그인을 진짜로** (F1 ⑤)
  - 확인: 틀린 인증번호를 넣으면 "인증번호가 맞지 않아요. 한 번 더 확인해주세요."가 보이고 넘어가지 않는다
~~~

- 제목은 `# {순번} · {묶음 이름}`. 플로우 묶음이면 FLOWS의 플로우 이름을 쓰고, 아니면 할 일을 짧게(`# 03 · Next.js로 옮기기`).
- 작업 기록은 SPEC.md에 두지 않는다. build-slice가 `docs/work/LOG.md`에 남긴다.

### 결정 기록 — docs/DECISIONS.md

저장할 때 이 단계에서 정한 것을 한 줄씩 추가한다(형식은 기존 표와 같다. 파일이 없으면 헤더째 만든다):
- 스택과 이유 (처음 한 번)
- 흉내만 내기로 한 것 중 영향이 큰 것(로그인처럼 나중에 다시 손봐야 하는 것)
- 2-4에서 물어서 정한 것

```markdown
| D-00N | <YYYY-MM-DD> | build-spec | 스택: 프로토타입 (Vite + React) | 첫 버전에 비밀 키가 필요한 기능이 없음 · 버린 안: Next.js | 유효 |
```

사용자가 고르거나 확인한 것만 적는다. 스택을 바꾸면 새 줄을 추가하고 기존 줄 상태를 `번복 → D-00N`으로 고친다.

SETUP.md와 SPEC.md는 html 리포트를 만들지 않는다. 체크리스트로 쓰는 작업 문서라서 md로 충분하다.

### 보고와 다음 안내

저장 후 짧게 보고한다: 고른 스택, 흉내만 낼 것, 만든 묶음 폴더와 조각 수. 그리고:

- **처음 실행 후:**
  > `docs/work/`에 정해둔 것(SETUP.md)과 첫 작업 묶음({폴더 이름})을 만들었어요. 이제 **build-slice**로 조각 1부터 만들어요. 조각 하나가 끝날 때마다 화면에서 직접 확인하고 저장(커밋)하니까, 중간에 멈춰도 다음에 build-slice를 다시 부르면 이어서 할 수 있어요.
- **새 묶음을 만든 뒤:**
  > 작업 묶음 {폴더 이름}에 조각 {개수}개를 만들었어요. build-slice로 시작해요.
- **스택을 바꾼 뒤:**
  > 스택을 {새 스택}으로 바꾸고 옮기기 묶음({폴더 이름})을 만들었어요. build-slice가 화면부터 그대로 옮길게요.
